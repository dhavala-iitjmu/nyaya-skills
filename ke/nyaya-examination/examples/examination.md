# Worked examination and adversarial contrasts

## A scoped inference that can pass

Supplied synthetic policy: a revision is eligible for staging if both unit and
integration checks pass. Supplied signed records show both passed for revision C.
Revision D is a supplied example meeting the same rule; revision E passes only
unit checks and is not eligible. No production release is authorized.

Expected examination:

- Pakṣa: revision C. Sādhya: eligibility under this staging policy.
- Hetu: the two required passing check records, established of C by supplied
  records, subject to their stated provenance. The examiner sees the records,
  not the test execution itself.
- Claimed connection: the stipulated policy's sufficient condition, not an
  empirically discovered universal law of bug-freedom.
- Dṛṣṭānta: D illustrates the policy; E shows why a weaker “unit checks alone”
  reason is insufficient. Neither example independently proves the policy.
- Five-member presentation, if needed: C is eligible; both checks passed; under
  the supplied policy that combination suffices, as illustrated by D; C meets
  that condition; therefore C is eligible under that policy only.
- Tarka can test the weaker rule against E, but creates no new experimental
  evidence. Graduate this scoped conclusion if record provenance is adequate.
  Do not conclude C has no bugs or execute a release.

## The same method must change these dispositions

| Supplied case | Required outcome and specific reason |
| --- | --- |
| Three reviewers cite one unverified blog as three independent observations | Trace śabda transmission to one origin; distinguish their reading from observing the reported event. Independent corroboration remains unknown. |
| “Every visible object is hot; the hill is visible, therefore it is hot,” with a supplied visible cold stone | Hetu may be present on the hill but the proposed vyāpti fails on the supplied dissimilar case; reject this inference without inventing another reason. |
| A model wins on one validation split, so it will beat the baseline on every deployment | Identify subject/target/reason, the unestablished general connection and omitted dataset/workload conditions. A scoped measured result may survive; the universal claim does not. |
| An unfamiliar artifact resembles an administrator credential, so it has administrator permissions | Resemblance does not establish authorization. A recognized name/kind and an unseen permission property require different warrant. |
| “If theory T were true, this output would occur; it occurred, so T is proved” | A favorable conditional consequence does not establish its premise. Tarka is not independent observation or a way to affirm the consequent. |
| A verified checksum matches; request is only to report whether this file matches | Report the bounded tool result with its acquisition chain. No compulsory five-part debate or invented defeater. |

The last case is a positive control against ceremonial overuse. The failure cases
must preserve whatever weaker claim is supported, rather than rejecting all
knowledge or making an endless evidence demand.

## Schema incompatibility

If the caller requests a full examination but permits only a Boolean `accepted`
field, do not silently drop a blocking evidence/source limitation. Use the host's
error/clarification channel to request a compatible contract. Do not fabricate new
top-level fields in a strict schema or return accepted merely because the argument
can be formatted. The host must provide a route to record consequential doubt.
